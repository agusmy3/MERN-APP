# mern-app

Aplikasi admin full-stack MERN (MongoDB, Express, React, Node.js) untuk mengelola data master (**Kategori, Produk, Vendor, Customer, UoM, Variant, Gudang, Outlet, Menu**) **stok** (Stock Adjustment / Opname, Stock Transfer antar gudang, kartu stok per gudang), **pembelian** (Purchase Order, Goods Receipt + biaya angkut, HPP rata-rata, tagihan vendor / hutang, pembayaran vendor, retur pembelian), dan **penjualan** (Quotation -> Sales Order (batas kredit) -> Delivery Order / surat jalan -> invoice (boleh gabungan beberapa surat jalan), cetak dokumen, Sales Invoice langsung dengan HPP & laba kotor, retur, pembayaran / piutang, price list, laporan), **POS** (kasir per outlet dengan shift), dengan autentikasi JWT dan otorisasi berbasis role (RBAC: **User, Role**). Sidebar aplikasi dibangun secara dinamis dari data Menu di database.

## Struktur

```
mern-app/
├── backend/   Express 5 + Mongoose 8 (CommonJS)
└── frontend/  React 19 + Vite 7 + Tailwind CSS 4 (ESM)
```

Tidak ada package.json di root; backend dan frontend dijalankan terpisah.

## Menjalankan

**Backend** (`backend/`):
```
npm run dev      # node --watch server.js, auto-restart saat file berubah
npm start        # node server.js
npm test         # semua test (unit + API); npm run test:unit | test:api | test:watch
npm run init -- --wipe --email=<email> --password=<password> [--name=] [--pkp=true|false] [--ppn=11] [--price-includes-tax=true|false]
                 # DEPLOY BARU: MENGHAPUS SELURUH DATABASE, lalu koleksi & index, System Settings, semua menu (config/menus.js),
                 # role Super Admin + role standar (config/roles.js), 1 Super Admin, customer walk-in.
                 # Wajib --wipe; NODE_ENV=production (backend/.env) wajib juga --force. Email/password bisa dari ADMIN_EMAIL/ADMIN_PASSWORD
npm run demo -- --password=<password user demo> [--pin=<PIN POS Store Supervisor>]  # data contoh SETELAH init (ditolak jika sudah ada gudang/produk/transaksi):
                 # 2 gudang, 2 outlet (lokasi lengkap), UoM & varian umum, 4 kategori, 6 produk + barcode + harga vendor + kemasan jual (air mineral PACK/DUS, keripik DUS), stok awal ber-HPP,
                 # reorder, price list, customer & vendor (lokasi lengkap), 1 user per role (@demo.local), PO terlambat, draft, invoice kredit,
                 # sales order + 1 surat jalan belum ditagih, batas kredit customer, 1 quotation terkirim (calon pembeli), 1 shift POS
# --- database LAMA (tanpa menghapus data) ---
npm run seed:admin -- --email=... --password=...  # Super Admin pertama, hanya jika belum ada user (atau ADMIN_EMAIL / ADMIN_PASSWORD / ADMIN_NAME di .env; password min. 8)
npm run seed:rbac  # migrasi RBAC (idempotent): role Super Admin -> admin@mern.com, tautkan Menu ke resource, buat menu User, Role, Audit Log, System Settings, Warehouse, grup Inventory (Stock Adjustment, Stock Transfer, Stock Movement, Reorder, Stock Valuation, Cost Revaluation) & grup Purchasing (Purchase Order, Goods Receipt, Vendor Bill, Vendor Payment, Purchase Return), grup Sales (Quotation, Sales Order, Delivery Order, Sales Invoice, Sales Return, Sales Payment, Price List, Sales Report), grup POS (Cashier, POS Shift) & menu Customer, Outlet
npm run menu:organize  # rapikan menu ke susunan standar (Dashboard, Master Data, Inventory, Purchasing, Sales, POS, Settings); default dry-run, `-- --apply` untuk menerapkan (backup JSON di backend/backups/, diabaikan git; audit log)
npm run migrate:produk-sku  # migrasi produk lama (idempotent): UoM PCS, 1 SKU default per produk (harga -> hargaJual, qty -> stok)
npm run migrate:stock-opening  # (idempotent) gudang MAIN + 1 dokumen Saldo Awal (POSTED) untuk stok SKU yang belum punya kartu stok; argumen opsional: kode gudang
npm run migrate:avg-cost       # (idempotent) HPP awal SKU yang kosong = harga vendor utama / termurah per satuan dasar
npm run seed:defaults          # (idempotent) data bawaan: customer "Umum / Walk-in" (sudah termasuk di init)
npm run migrate:uom-type       # (idempotent) isi jenis UoM yang kosong dari kodenya (PCS -> Count, KG -> Weight, BOX -> Package), laporkan harga vendor yang konversinya tidak cocok
npm run migrate:audit-gudang  # (idempotent) isi `gudangs` pada log audit lama dokumen per gudang (sebelum dijalankan, log lama terlihat oleh semua gudang)
npm run migrate:sales-lines   # (idempotent) kemasan jual: _id baris SO / invoice, tautan soLine (surat jalan) & invoiceLine (retur) untuk data lama (WAJIB sekali di database lama)
npm run migrate:invoice-deliveries  # (idempotent) invoice dari surat jalan: salesOrder/deliveryOrder tunggal -> salesOrders/deliveryOrders + soAllocations (WAJIB sekali di database lama yang sudah punya invoice dari DO)
npm run stock:reconcile        # cek StockBalance & ProdukSku.stok vs kartu stok; `-- --fix` menulis ulang cache dari movement
npm run rs:init  # inisialisasi replica set 1 node (idempotent; biasanya lewat setup-replica-set.ps1)
```
Butuh `backend/.env` dengan `MONGO_URI`, `JWT_SECRET`, `PORT` (default 5000).

**Deploy baru:** aktifkan replica set (di bawah), lalu `npm run init -- --wipe --email=... --password=...` (+ `npm run demo -- --password=...` untuk data contoh). **Database lama** (tanpa menghapus): `seed:rbac`, `menu:organize -- --apply`, `seed:defaults`, `migrate:*` (semua idempotent; termasuk `migrate:invoice-deliveries`, `migrate:sales-lines` & `migrate:audit-gudang`). Susunan menu standar = [config/menus.js](backend/config/menus.js) (dipakai `init` & `menu:organize`), role standar = [config/roles.js](backend/config/roles.js) (Owner / Manager, Admin Master Data, Warehouse Staff, Warehouse Supervisor, Purchasing, Sales Admin, Finance, Cashier, Store Supervisor; data biaya hanya Owner, Warehouse Supervisor, Purchasing, Finance; Warehouse Staff hanya draft dokumen stok & surat jalan, posting oleh Supervisor; Sales Admin membuat quotation, SO & invoice dari surat jalan; Finance mengatur batas kredit & menyetujui SO melewati batas, mencatat pembayaran vendor; Purchasing membuat tagihan vendor & draft retur pembelian, Warehouse Supervisor memposting retur). Test `test/scripts/init-demo.test.js` menjalankan kedua script ke MongoDB sementara.

**MongoDB wajib replica set** (untuk transaksi). Standalone -> backend berhenti saat start dengan petunjuk. Setup sekali di Windows (PowerShell *Run as Administrator*, dari `backend/`):
```
powershell -ExecutionPolicy Bypass -File .\scripts\setup-replica-set.ps1
```
Script: backup + tambah `replication` (`replSetName: rs0`, `oplogSizeMB: 1024`) di `mongod.cfg`, restart service `MongoDB`, `rs.initiate`, lalu tambah `replicaSet=rs0` ke `MONGO_URI`.

**Frontend** (`frontend/`):
```
npm run dev      # Vite dev server, proxy /api -> http://localhost:5000
npm run build
npm run lint     # ESLint
npm test         # test utilitas (node:test)
```

### Test

- **Backend** (`backend/test/`, runner bawaan `node:test`, tanpa dependensi tambahan):
  - `unit/`: fungsi murni (number, HPP & pembelian, permissions, audit diff).
  - `api/`: lewat HTTP ke app sungguhan (`fetch` ke `app.listen(0)`): RBAC, stok, pembelian, HPP, konkurensi/rollback, menu, reorder, dashboard.
  - [test/helpers/mongo.js](backend/test/helpers/mongo.js) menjalankan **mongod lokal** sebagai replica set sementara (port acak, folder temp, dihapus setelah selesai) per file test; lokasi mongod dari env `MONGOD_BIN` atau path instalasi default.
  - [test/helpers/setup.js](backend/test/helpers/setup.js): `const t = useTestApp()` lalu `const admin = await t.loginAs()` / `t.loginAs({ produk: ['update'] })` -> client `get/post/put/del` yang mengembalikan `{ status, data, message }`. [factory.js](backend/test/helpers/factory.js): `createMasters`, `createProduct`, `postAdjustment`, `ok(res, status)`.
  - **Fitur / endpoint baru wajib disertai test API-nya.**
- **Frontend** (`frontend/test/`, `node:test` + resolver import tanpa ekstensi di `test/register.mjs`): fungsi utilitas di `src/utils`. Test komponen (Vitest + React Testing Library) menyusul setelah dependensinya dipasang.

## Backend

- Entry: [backend/server.js](backend/server.js) (dotenv, koneksi DB, listen) memakai [backend/app.js](backend/app.js) (CORS, JSON body, header `Cache-Control: no-store`, mount route; **tanpa** koneksi DB / listen, supaya bisa dipakai test).
- Pola per resource: `models/` → `controllers/` → `routes/`.
- Route yang terdaftar:
  - `/api/auth`: `POST /login` (publik), `GET /me` (profil + role + izin efektif), `PUT /theme`. **Registrasi publik dimatikan**; user dibuat admin lewat `/api/user`.

  - `/api/role`: `GET /resources` (registri untuk matriks), `GET /dropdown`, CRUD standar. `/api/user`: CRUD standar (tanpa `/all`).
  - `/api/produk/:id/sku`: `GET` (list SKU + `packages` + harga pokok jika boleh lihat harga vendor), `POST /generate` (kombinasi varian), `PUT` (bulk update), `PUT /:skuId/packages` (`{ packages: [{ uom, konversi, hargaJual, barcode, isActive }] }` kemasan jual, mengganti daftar), `DELETE /:skuId`. Mengelola SKU butuh izin `produk:update`.

  - `/api/stock-transfer` (resource `stockTransfer`, + action `post`): `GET /` (filter `search|status|fromGudang|toGudang|gudang|from|to`, + `lineCount`, `totalQty`, `totalReceived`, `totalValue`), `GET /:id` (+ `currentQty` draft, `canSend`/`canReceive`, biaya untuk `vendorPrice:view`), `GET /skus`, `POST /skus/balance` (handler Stock Adjustment), `POST` / `PUT /:id` / `DELETE /:id` (draft), `POST /:id/send`, `POST /:id/receive` (`{ lines: [{ sku, qtyReceived }], note }`), `POST /:id/cancel` (`{ reason }`, hanya IN_TRANSIT).

### Otorisasi (RBAC)

- Satu user = satu role (`User.role`). Izin disimpan di `Role.permissions: [{ resource, actions }]`, action: `view` (buka menu, tabel, search, detail), `create`, `update`, `delete`, `approve` (hanya `salesOrder`: konfirmasi melewati batas kredit, juga syarat mengubah `Customer.creditLimit`), dan `post` (hanya resource yang mendeklarasikannya, mis. `stockAdjustment`: posting/pembatalan dokumen stok, supaya pembuat draft dan pemosting bisa dipisah). Action selain `view` hanya sah jika `view` juga ada.
- Registri resource: [config/permissions.js](backend/config/permissions.js) (sumber kebenaran; juga dikirim ke frontend lewat `GET /api/role/resources`).
- **Setiap endpoint data wajib `protect` + `authorize(resource, action)`** ([middlewares/authorize.js](backend/middlewares/authorize.js)); tanpa izin -> **403** (bukan 401). Pola route: `GET /`, `GET /:id`, `GET /all` -> view; `POST` -> create; `PUT` -> update; `DELETE` -> delete.
- `GET /dropdown` cukup `protect` (tanpa izin view), untuk pilihan di form resource lain; **hanya field ringkas** (`_id` + `name`/`code`) via `dropdownHandler` di [helpers/dropdownHelper.js](backend/helpers/dropdownHelper.js). Daftarkan sebelum `/:id`.
- Role `isSystem` (Super Admin) melewati semua cek, tidak bisa diubah/dihapus. Backend mencegah: hapus role yang masih dipakai, ubah role/nonaktifkan/hapus akun sendiri, dan kehilangan Super Admin aktif terakhir.
- `Menu.resource` menautkan menu ke resource: sidebar (`/api/menu/tree`) hanya memuat menu yang boleh di-view; menu tanpa resource tapi punya route = semua user; menu grup tampil jika ada anak yang tampil.
- Resource tanpa `actions` = `view/create/update/delete`; resource boleh membatasi/menambah action-nya (`actions: ['view']` untuk `auditLog` & `stockMovement`, `+ 'post'` untuk `stockAdjustment`). `GET /api/role/resources` mengirim daftar action efektif per resource; matriks Role menampilkan "–" untuk action yang tidak berlaku. UI: `usePermission(...).canPost` / `.canApprove`.
- **Akses gudang** ([helpers/gudangAccess.js](backend/helpers/gudangAccess.js)): `User.allGudang` (default true, juga user lama) / `User.gudangs`; Super Admin selalu semua gudang. `gudangScope(req)` (null = semua), `assertGudang(req, ...ids)` (403), `applyGudangFilter(req, filter, req.query.gudang)` untuk daftar. Dibatasi: dokumen stok, transfer, PO/GR, kartu stok, valuasi, reorder, dashboard. **Jumlah** stok gudang lain tetap boleh dilihat (tab Stock produk, tanpa nilai; kartu stoknya terkunci). `GET /api/gudang/dropdown` menandai `accessible`; frontend `getMyGudangDropdown` = hanya yang accessible. `GET /api/auth/me` mengirim `gudangAccess: { all, gudangs }`. **Endpoint baru yang memakai gudang wajib memakai helper ini.** Audit Log disaring per gudang: setiap log dokumen per gudang menyimpan `gudangs` (`GUDANG_OF` di auditLogger; transfer = asal & tujuan, pembayaran = gudang invoice / tagihan), log terlihat jika salah satu gudangnya boleh diakses; log tanpa gudang (master, setting, user) tidak disaring (`gudangLogFilter` dipakai Audit Log global, histori, dan aktivitas dashboard).
- Menambah resource baru: tambah di `RESOURCES`, pasang `authorize` di route, guard di `App.jsx`, `resource` di `useCrudDrawer` halaman, lalu set Permission di data Menu.

### Transaksi

- **Semua endpoint tulis** dibungkus `runInTransaction` ([helpers/transaction.js](backend/helpers/transaction.js)); session diteruskan otomatis (`transactionAsyncLocalStorage`), jadi query di dalamnya tidak perlu `{ session }`.
  ```js
  const doc = await runInTransaction(async () => {
    const doc = await Model.findById(id);                       // baca DI DALAM transaksi
    if (!doc) throw new HttpError('Not found', 404);            // throw = semua perubahan batal
    await lock(ref('kategori', doc.kategori));                  // lihat aturan lock di bawah
    ... tulis data + audit.log*() ...
    return doc;
  });
  return successResponse(res, doc, ...);                         // response DI LUAR transaksi
  ```
  `handleError` tiap controller memetakan `HttpError` ke status-nya.
- Callback bisa **dijalankan ulang otomatis** saat bentrok dengan transaksi lain: isinya hanya operasi database (tanpa kirim response / API luar). Validasi input murni boleh di luar.
- **Write skew**: transaksi hanya bentrok jika menulis dokumen yang sama, jadi aturan lintas dokumen butuh `lock(key)` (dokumen di koleksi `txlocks`) di semua transaksi yang menyangkut aturan tsb:
  - `ref('<entity>', id)`: hapus Kategori/UoM/Variant/Vendor/Role/Menu/Produk <-> create/update yang mereferensikannya (produk, SKU, harga vendor, user, sub-menu).
  - `ref('gudang', id)`: hapus Gudang <-> dokumen stok baru / posting di gudang tsb. Draft stok juga mengunci `ref('produk', ...)` tiap SKU-nya (hapus SKU/produk mengecek pemakaian di dokumen stok).
  - `preferred:<skuId>`: maks. 1 vendor utama per SKU. `superadmin`: min. 1 Super Admin aktif.
  - **Stok**: saldo dibaca lalu ditulis di transaksi yang sama (`applyMovements`), jadi dua posting untuk SKU+gudang yang sama pasti bentrok dan salah satu diulang dengan saldo terbaru; tidak perlu `lock`.

### Stok

- **Stok hanya berubah lewat dokumen** (sekarang: Stock Adjustment; nanti pembelian/penjualan/transfer) melalui `applyMovements(req, entries, { refType, refId, refNo, isReversal })` di [helpers/stockHelper.js](backend/helpers/stockHelper.js), di dalam `runInTransaction`. **Jangan** menulis `ProdukSku.stok` / `StockBalance` langsung; `PUT /api/produk/:id/sku` mengabaikan field `stok`.
- Tiga lapis: `StockMovement` (kartu stok, **append-only**, sumber kebenaran, `balanceAfter` per SKU+gudang) -> `StockBalance` (saldo per SKU + **gudang**, cache) -> `ProdukSku.stok` (total semua gudang, cache). `npm run stock:reconcile` memeriksanya.
- Stok **tidak boleh minus**: satu baris minus -> `HttpError` -> seluruh dokumen batal. Kesalahan dikoreksi dengan **Cancel** (movement pembalik `isReversal`), tidak ada yang dihapus. Movement tidak dicatat di AuditLog (dokumennya yang diaudit).
- **Angka maks. 2 desimal** (stok, qty, harga, konversi, min. order): validasi `checkAmount()` dan pembulatan `round2()` dari [helpers/number.js](backend/helpers/number.js) (frontend: `round2`, `formatNumber`, `formatSigned` di `utils/formatHelper.js`; input `step="0.01"`).
- Dokumen `StockAdjustment` (1 dokumen = 1 gudang): `DRAFT -> POSTED -> CANCELLED`. Jenis `ADJUSTMENT` (user mengisi `qtyChange` +/-, alasan wajib) dan `OPNAME` (user mengisi `qtyActual`; `qtySystem` & selisih diambil **saat Post**). Nomor `ADJ-/OPN-YYYYMM-NNNN` dari koleksi `counters` (`nextDocNo`, di dalam transaksi). Alasan & konstanta: [config/stock.js](backend/config/stock.js) (salinan frontend: `utils/stockMeta.js`); alasan `OTHER` wajib catatan, `OPENING` -> movement `OPENING`.
- SKU/produk yang sudah punya movement **atau** dipakai dokumen stok tidak bisa dihapus (400, arahkan ke nonaktifkan). Gudang dengan saldo/movement/dokumen tidak bisa dihapus; gudang nonaktif tidak bisa dipakai untuk dokumen baru.
- **HPP (average cost)**: `ProdukSku.avgCost`, moving weighted average **per SKU untuk semua gudang**, 2 desimal, `null` = belum diketahui. Dihitung di `applyMovements`: baris dengan `unitCost` (Goods Receipt, dan pembaliknya saat cancel) mengubah HPP; baris lain dicatat dengan `unitCost` = HPP saat itu. Setiap movement menyimpan `unitCost`, `value` (qty x unitCost), `avgCostAfter`. HPP & nilai = data biaya: hanya dikirim ke user dengan `vendorPrice:view` (kartu stok + `canSeeCost`, list SKU, pencarian SKU dokumen, nilai Stock Adjustment: draft = perkiraan perubahan x HPP saat ini, posted = `value` movement-nya, list = `totalValue`).
- **Mengisi HPP stok yang belum punya HPP**: (1) Stock Adjustment alasan **Opening Balance**: baris yang menambah stok bisa diberi `unitCost` (wajib saat post bila SKU belum ber-HPP) dan ikut menghitung HPP rata-rata; hanya diisi/dilihat user dengan `vendorPrice:view` (user lain mengedit draft -> harga pokok yang ada dipertahankan). (2) **Cost Revaluation** ([costRevaluationController](backend/controllers/costRevaluationController.js)): ganti HPP tanpa mengubah stok; post menyimpan `oldCost`, `qty`, `valueChange` per baris + movement `REVALUATION` (qty 0, `value` = saldo gudang x selisih) per gudang; cancel hanya jika HPP SKU belum berubah lagi.
- **Reorder** ([reorderController](backend/controllers/reorderController.js)): `ReorderRule` min/max per **SKU + gudang** (satuan dasar). **Tersedia = stok − dipesan customer** (sisa SO OPEN/PARTIAL, `committedMap`). Status: `OK` (tersedia > min), `OUT` (tersedia <= 0 dan belum tertutup), `CRITICAL` (tersedia <= min dan tersedia + sedang dipesan <= min), `ORDERED` (tertutup PO OPEN/PARTIAL / transfer masuk). Saran = max − (tersedia + sedang dipesan), dikonversi ke satuan beli vendor utama (dibulatkan ke atas, min. order). SKU/gudang nonaktif diabaikan; hapus SKU/produk/gudang ikut menghapus rule-nya. Rule diaudit (entity `reorderRule`, parent produk).
- **Stock Transfer** ([stockTransferController](backend/controllers/stockTransferController.js)): 2 langkah `DRAFT -> IN_TRANSIT (send) -> RECEIVED`, `IN_TRANSIT -> CANCELLED`. Send = `TRANSFER_OUT` di gudang asal, HPP saat itu disimpan per baris; receive = `TRANSFER_IN` di gudang tujuan dengan unitCost yang sama (nilai hanya berpindah). Terima kurang dari dikirim boleh (selisih = hilang/rusak di perjalanan, catatan wajib, `lossValue`), lebih ditolak. Cancel hanya sebelum diterima (pembalik ke gudang asal); sesudahnya buat transfer balik. Draft/kirim/batal butuh akses gudang asal, terima butuh akses gudang tujuan. Barang **in transit** tidak ada di saldo gudang mana pun: `inTransitSummary()` dipakai valuasi (`totals.inTransit`), dashboard, dan reorder (dihitung "sedang dipesan" di gudang tujuan). Nomor `TRF-YYYYMM-NNNN`.
- Rencana: outlet (POS) menunjuk ke gudang + penugasan kasir -> outlet, dibuat bersama modul POS.

### Penjualan

- **Kemasan jual** ([helpers/packageHelper.js](backend/helpers/packageHelper.js)): `ProdukSku.packages: [{ _id, uom, konversi (isi satuan dasar, > 1), hargaJual (null = isi x harga satuan), barcode (unik terhadap semua barcode SKU & kemasan), isActive }]`; jenis satuan harus cocok (aturan konversi pembelian `assertConvertible`); kemasan yang dipakai dokumen / price list tidak bisa dihapus (nonaktifkan); satuan dasar produk tidak bisa diganti selama ada kemasan; UoM yang dipakai kemasan / dokumen tidak bisa dihapus. Baris **Quotation, Sales Order, Sales Invoice, Delivery Order**: `uom` (satuan jual; data lama null = satuan dasar), `konversi`, `qtyUom` (qty satuan jual; null = `qty`), **`qty` = satuan dasar** (stok, HPP, dipesan, Reorder, kredit, laporan tetap satuan dasar), `hargaJual` & `subtotal` per satuan jual (`salesLineSubtotal` memakai `qtyUom ?? qty`). Input API baris: `{ sku, uom?, qty (dalam satuan jual) }`; `applyUnits` mengisi isi dari master (input diabaikan), qty kemasan **wajib bulat**, baris unik per **SKU + satuan** (SKU sama boleh beberapa satuan). Harga (`resolveUnitPrices`): price list customer (SKU + satuan) -> harga kemasan -> isi x harga satuan dasar (price list / SKU). Pencarian SKU penjualan mengembalikan `units` (satuan dasar + kemasan aktif dengan harga customer) & `matchedUom` (scan barcode kemasan); `POST .../skus/prices` menerima `{ customer, items: [{ sku, uom }] }` -> kunci `sku:uom` (`sku:` = satuan dasar). Baris SO & invoice punya `_id`: **surat jalan** merujuk `soLine` (kemasan sama dengan SO, qty dalam kemasan tsb, bulat; input lama `{ sku }` hanya jika SKU tsb 1 baris), **retur** merujuk `invoiceLine` dengan qty **satuan dasar** (bisa retur sebagian isi dus; nilai proporsional baris). Invoice dari surat jalan menggabung per SKU + kemasan + harga + diskon (beda = baris terpisah). **POS**: scan barcode kemasan (`/api/pos/skus` -> `exact` + `matchedUom`), keranjang per SKU + satuan (boleh campur kemasan), `POST /api/pos/sales` baris `{ sku, uom?, qty (satuan jual) }`, hold menyimpan satuan (`PosHold.lines.uom`; kemasan nonaktif saat dilanjutkan -> dilewati), `/api/pos/prices` `{ customer, items }`, retur kasir per baris transaksi `{ invoiceLine, qty satuan dasar }`, struk `2 PAK x 22.000` + `= 12 BTL`.
- **Customer** ([customerController](backend/controllers/customerController.js)): master standar + `isActive` + lokasi lengkap (`address` = alamat jalan, + `provinsi`, `kota`, `kecamatan`, `kodePos`, `latitude`/`longitude`; validasi `parseRegion` di [helpers/locationHelper.js](backend/helpers/locationHelper.js), sama untuk Vendor dengan `companyAddress`; form: [RegionFields](frontend/src/components/RegionFields.jsx) + `utils/regionMeta.js`). Customer bawaan **Umum / Walk-in** (`isWalkIn`, maks. 1, dibuat `seed:defaults` / `ensureWalkInCustomer()`): default dokumen penjualan, tidak bisa dihapus / dinonaktifkan. Customer nonaktif tidak bisa dipakai dokumen baru; yang sudah dipakai invoice tidak bisa dihapus.
- **Sales Order** ([salesOrderController](backend/controllers/salesOrderController.js)) = pesanan customer (`SO-…`), **tidak mengubah stok**; 1 SO = 1 customer (bukan walk-in) + 1 gudang: `DRAFT -> OPEN (confirm) -> PARTIAL -> DELIVERED`, `CLOSED` (dari PARTIAL, sisa tidak dikirim) & `CANCELLED` (dari OPEN); hanya DRAFT yang bisa diedit / dihapus; cancel / close ditolak selama ada draft DO. Harga **dibekukan** seperti invoice (price list / harga jual, dihitung ulang tiap draft disimpan), diskon baris & dokumen, pajak dari setting. `deliveryMethod` `DELIVERY` (alamat kirim `shipTo` wajib, default alamat customer, bisa diganti per SO) / `PICKUP` (tanpa alamat & ongkir). `requestedDate`, `customerPoNo`. **Stok dipesan** ([helpers/salesOrderHelper.js](backend/helpers/salesOrderHelper.js) `committedQty`) = sisa baris SO OPEN/PARTIAL per SKU+gudang; tersedia = stok - dipesan; **hanya informasi** (tidak mengunci stok; SO melebihi stok hanya peringatan); dihitung di Reorder. Dari quotation: `SalesOrder.quotation`, harga baris = harga penawaran (juga saat draft diubah; SKU baru = harga biasa).
- **Batas kredit** (`Customer.creditLimit`, 0 = tanpa batas; hanya bisa diubah user dengan `salesOrder:approve`): `customerCredit()` ([helpers/salesOrderHelper.js](backend/helpers/salesOrderHelper.js)) = piutang (invoice POSTED belum lunas) + nilai SO belum ditagih (SO OPEN/PARTIAL: qty dipesan, SO DELIVERED/CLOSED: qty terkirim; dikurangi qty surat jalan yang sudah ber-invoice; termasuk PPN & ongkir yang belum ditagih) + `overdue`. Saat **konfirmasi SO** (di dalam transaksi, customer dikunci): exposure + total SO > limit, atau (setting `sales.blockOverdue`, default true) ada invoice lewat jatuh tempo -> 409 `CREDIT_BLOCK`; user `salesOrder:approve` bisa tetap konfirmasi dengan alasan (`creditOverrideReason`, `creditOverrideNote` posisi saat itu, `creditOverrideBy/Date`, diaudit). Hanya di konfirmasi SO (invoice langsung / POS tidak dicek).
- **Quotation** ([quotationController](backend/controllers/quotationController.js), `QUO-…`): penawaran, tidak mengubah stok & tidak dihitung dipesan. `DRAFT -> SENT -> ACCEPTED` (konversi) / `REJECTED` (alasan); `SENT -> DRAFT` (revise); SENT lewat `validUntil` = kedaluwarsa (`expired`, dihitung saat dibaca; tidak bisa dikonversi). Harga dibekukan seperti SO, **dikunci sejak dikirim** (send menghitung ulang sekali). Customer boleh walk-in (wajib `prospectName`), konversi lalu wajib memilih customer bernama. Konversi = SO **DRAFT** (`createDraftFromQuotation`: gudang, metode, baris, diskon, ongkir, pajak disalin; alamat kirim = alamat customer), quotation ACCEPTED + `salesOrder`. `terms` dicetak. Customer / gudang / SKU yang dipakai quotation tidak bisa dihapus.
- **Delivery Order / surat jalan** ([deliveryOrderController](backend/controllers/deliveryOrderController.js), `DO-…`): dari SO OPEN/PARTIAL (banyak DO per SO), gudang / customer / metode / alamat disalin dari SO; `DRAFT -> POSTED -> CANCELLED`. Qty <= sisa SO (dicek lagi saat post, `lock(ref('salesOrder', id))`). **Post = stok keluar** (movement `SALE`, refType `DeliveryOrder`, HPP saat itu per baris) + `qtyDelivered` & status SO. Cancel = pembalik (hanya jika belum ditagih; SO CLOSED tetap CLOSED). Data kirim: `vehicleNo`, `driverName`, `courier`, `trackingNo`; pickup: `pickedUpBy`. Cetak surat jalan (A4, **tanpa harga**): `utils/documentPrint.js`.
- **Invoice dari DO** (`invoiceDeliveries` di deliveryOrderController; `POST /api/delivery-order/:id/invoice` atau gabungan `POST /api/delivery-order/invoice`): 1 invoice = **1 atau beberapa DO** POSTED belum ditagih dengan **customer & gudang sama** (boleh lintas SO, tarif PPN & mode harga SO harus sama), langsung POSTED (`source: 'SALES_ORDER'`, `salesOrders`, `deliveryOrders`, `soAllocations: [{ salesOrder, subtotal, discountAmount, shippingCharge }]`; `DeliveryOrder.invoice`), **tanpa movement** (stok sudah keluar di DO; `cogs` dari HPP DO). Baris digabung per SKU (harga & diskon harus sama, beda -> tagih terpisah; returnya tetap per SKU). Per SO: diskon dokumen dibagi proporsional subtotal (invoice yang melengkapi qty SO memakai sisanya, qty ditagih dihitung dari DO ber-invoice), ongkir ditagih di invoice pertama SO tsb (dari `soAllocations` invoice aktif); jatuh tempo = tanggal + termin customer. Cancel invoice ini tidak mengubah stok, semua DO-nya jadi "belum ditagih" lagi. Retur & pembayaran memakai alur invoice biasa.
- **Ongkir** (`shippingCharge`, ditentukan di SO, hanya DELIVERY): ditagih penuh di invoice **pertama** (yang tidak dibatalkan) dari SO tsb; mengikuti mode pajak dokumen (kena PPN). `salesTotals` ([helpers/salesHelper.js](backend/helpers/salesHelper.js)): `dpp` = **DPP barang saja** (= penjualan bersih, laba kotor tidak termasuk ongkir), `shippingDpp` (tanpa PPN) & `shippingTotal` (termasuk PPN) terpisah, `taxAmount` & `total` termasuk ongkir. Retur tidak mengembalikan ongkir (`goodsTotal(inv)` = total - shippingTotal). Laporan penjualan: `totals.shipping`.
- **Sales Invoice** ([salesInvoiceController](backend/controllers/salesInvoiceController.js)) = penjualan langsung (barang keluar + invoice dalam 1 dokumen; pesanan bertahap lewat Sales Order di atas), 1 dokumen = 1 gudang: `DRAFT -> POSTED -> CANCELLED`. Nomor `INV-YYYYMM-NNNN`. Baris: `sku`, `qty`, `hargaJual` (**dibekukan**: selalu diisi backend dari price list customer / harga jual SKU setiap draft disimpan, input klien diabaikan; potongan harga hanya lewat diskon), `diskonPersen`, `subtotal`, `unitCost` (saat post); **satuan dasar saja** (kemasan jual menyusul). Diskon dokumen nominal (`discountAmount` <= subtotal). SKU / customer / gudang nonaktif ditolak (dicek lagi saat post).
- **Pajak** ([helpers/salesHelper.js](backend/helpers/salesHelper.js), salinan frontend `utils/salesMeta.js`): `taxRate` default = PKP ? `tax.ppnRate` : 0, `priceIncludesTax` default dari setting `sales.priceIncludesTax` (false); keduanya disalin ke dokumen & bisa diubah selama draft. Exclusive: `dpp = subtotal - diskon`, `PPN = dpp x tarif`, `total = dpp + PPN`. Inclusive: `total = subtotal - diskon`, `PPN = total x tarif / (100 + tarif)`, `dpp = total - PPN`. **Penjualan bersih = `dpp`**.
- **Post** = movement `SALE` (-qty, stok tidak boleh minus -> seluruh dokumen batal), HPP saat itu disimpan per baris, `cogs` = Σ qty x HPP, **laba kotor = dpp - cogs**. **Cancel** = pembalik dengan unitCost yang sama. Jual di bawah HPP hanya peringatan (UI, untuk `vendorPrice:view`). HPP / margin / laba = data biaya (`vendorPrice:view`). Akses gudang berlaku. Invoice yang punya retur (draft/posted) atau pembayaran tidak bisa dibatalkan (batalkan itu dulu).
- **Retur** ([salesReturnController](backend/controllers/salesReturnController.js)): `RTN-…`, dari invoice POSTED (gudang = gudang invoice), `DRAFT -> POSTED -> CANCELLED`, alasan wajib. Qty <= terjual - sudah diretur (dicek lagi saat post; `lock(ref('salesInvoice', id))`). Post = movement `SALE_RETURN` (+qty, `unitCost` = HPP baris invoice) + `invoice.lines.qtyReturned` & `invoice.returnedAmount`. Nilai baris dibagi proporsional seperti invoice (`returnLineValues`: `amount` termasuk PPN = mengurangi tagihan, `netAmount` = mengurangi penjualan); retur terakhir memakai sisa nilai invoice (tanpa selisih pembulatan). Barang rusak tetap masuk stok, lalu dikeluarkan lewat Stock Adjustment. Cancel = pembalik (stok harus cukup).
- **Piutang** ([salesPaymentController](backend/controllers/salesPaymentController.js)): `Customer.termDays` (0 = tunai) -> `invoice.dueDate` default = tanggal + termin (bisa diubah selama draft). Sisa = `total - returnedAmount - paidAmount` (`invoiceBalance`), `paymentStatus` UNPAID / PARTIAL / PAID / OVERPAID disimpan di invoice (filter list `paymentStatus=OPEN|OVERDUE|...`). `SalesPayment` (`PAY-…` / refund `RFD-…`): 1 pembayaran = 1 invoice, boleh cicil; PAYMENT <= sisa, REFUND <= kelebihan bayar (mis. retur setelah lunas); batal dengan alasan. Dashboard: KPI piutang & lewat jatuh tempo.
- **Price list** ([priceListController](backend/controllers/priceListController.js), [helpers/priceHelper.js](backend/helpers/priceHelper.js) `resolvePrices`): `PriceList` (`code`, `name`, `isActive`, `items: [{ sku, produk, price }]`), `Customer.priceList`. Item per SKU + satuan (`uom` null = satuan dasar, selain itu kemasan jual SKU). Harga invoice = price list customer (aktif & SKU + satuan ada) atau `hargaJual` (kemasan: lihat Kemasan jual); ganti customer di draft -> harga baris diperbarui. Item ikut terhapus saat SKU / produk dihapus. Belum ada tingkatan qty / masa berlaku.
- **Laporan** ([salesReportController](backend/controllers/salesReportController.js)): penjualan bersih = dpp invoice (tanggal invoice) - `netAmount` retur (tanggal retur), HPP = qty x unitCost (retur mengurangi); umur piutang dari invoice belum lunas. Dashboard penjualan juga sudah dikurangi retur.
- **Cetak** ([utils/documentPrint.js](frontend/src/utils/documentPrint.js), A4, kop dari setting `company.*`): surat jalan (tanpa harga), Sales Order (konfirmasi pesanan), Invoice (jatuh tempo, retur, dibayar, sisa, instruksi bayar `company.bankInfo`), Quotation (masa berlaku, calon pembeli, syarat).
- **Pembayaran gabungan** (`CustomerReceipt` `RCV-…` / `VendorPaymentBatch` `VPB-…`, schema bersama [helpers/paymentBatchSchema.js](backend/helpers/paymentBatchSchema.js)): 1 uang masuk / keluar untuk beberapa invoice / tagihan dari 1 customer / vendor. Setiap alokasi = 1 `SalesPayment` / `VendorPayment` PAYMENT biasa dengan `batch` (jadi status bayar, umur piutang/hutang, laporan tidak berubah). Jumlah **harus = total alokasi** (kelebihan bayar / deposit belum didukung), tiap alokasi <= sisa, tanpa potongan / write-off. Batal = semua alokasi batal sekaligus; pembayaran ber-`batch` tidak bisa dibatalkan sendiri. Refund tetap per invoice. Cetak kuitansi / bukti pembayaran (`paymentBatchHtml`).
- Belum ada: deposit / uang muka customer, potongan (write-off) saat pembayaran, approval berjenjang, logo di kop dokumen, cek kredit di invoice langsung / POS, cetak tagihan / retur pembelian, logo di struk POS.

### POS

- **Outlet** ([outletController](backend/controllers/outletController.js)): toko dengan lokasi lengkap (alamat, provinsi, kota/kabupaten, kecamatan, kode pos, koordinat; validasi bersama Gudang di [helpers/locationHelper.js](backend/helpers/locationHelper.js)), **1 gudang sumber stok** (1 gudang boleh banyak outlet; gudang yang memasok outlet tidak bisa dihapus), `priceIncludesTax` (default true), `receiptHeader/Footer`, `receiptWidth` 58/80. Kasir ditugaskan lewat `User.outlets` (Super Admin semua; [helpers/posHelper.js](backend/helpers/posHelper.js) `canUseOutlet`). POS **tidak** memakai akses gudang user.
- **Shift** ([posController](backend/controllers/posController.js), model `PosShift`): wajib buka shift (modal awal) sebelum berjualan; **per kasir** (maks. 1 OPEN, unique partial index). Kas masuk/keluar dengan alasan (keluar <= kas di laci). `shiftSummary`: kas seharusnya = modal + pembayaran tunai POSTED (shift) - refund tunai + kas masuk - kas keluar. Tutup = uang fisik dihitung, `difference` (catatan wajib bila ada selisih); supervisor (`posShift:update`) bisa menutup shift kasir lain.
- **Transaksi** = `SalesInvoice` (`source: 'POS'`, `outlet`, `shift`, nomor `POS-…`) langsung POSTED & lunas dalam 1 transaksi: harga dibekukan (price list customer / harga jual), PPN tarif setting + `priceIncludesTax` outlet, diskon baris & transaksi, movement `SALE` dari gudang outlet (stok kurang -> batal). Pembayaran split (`CASH|CARD|QRIS|TRANSFER|OTHER`) -> `SalesPayment` per metode ber-`shift`; non-tunai <= total, total bayar >= total, **kembalian hanya dari tunai** (tunai dicatat bersih; `cashTendered` & `change` di invoice). Customer default walk-in. Pembayaran di shift yang sudah ditutup tidak bisa dibatalkan.
- **Barcode**: `ProdukSku.barcode` (opsional, unik partial index), diedit di tabel SKU produk; kosong = dihapus.
- **Hold / park** (model `PosHold`): keranjang ditahan di server per shift (maks. 10), stok tidak dikunci; kasir boleh melanjutkan (harga & stok terbaru, hold dihapus) atau membuang tanpa persetujuan; sisa hold dihapus saat shift ditutup. Tidak diaudit.
- **PIN supervisor** (`User.posPinHash` bcrypt, `select: false`; `hasPosPin` untuk tampilan; diatur di form User, `posPin` 4-8 digit, kosong = hapus): penyetuju = user aktif ber-izin `pos:post` yang ditugaskan di outlet (Super Admin semua). Verifikasi di LUAR transaksi (`verifyApprover`); 5x salah -> terkunci 15 menit (429).
- **Void** (`POST /api/pos/sales/:id/void`): hanya transaksi di **shift kasir yang masih terbuka** tanpa retur; stok kembali (pembalik SALE), semua pembayarannya dibatalkan (kas seharusnya turun), invoice CANCELLED + `voidApprovedBy`. Selain itu -> retur.
- **Retur di kasir** (`POST /api/pos/returns`): hanya di **outlet yang sama** dengan transaksi (shift mana pun); Sales Return langsung POSTED (`createPostedReturn` di salesReturnController, + `shift`, `outlet`, `approvedBy`), lalu refund = kelebihan bayar lewat metode pilihan (tunai: <= kas di laci) sebagai `SalesPayment` REFUND ber-`shift`.
- `shiftSummary` juga menghitung void & retur. Struk & laporan shift **X** (sementara) / **Z** (tutup) dicetak lewat `utils/receiptPrint.js`; `Outlet.autoPrint` = cetak struk otomatis setelah bayar.

### Pembelian

- **Purchase Order** ([purchaseOrderController](backend/controllers/purchaseOrderController.js)): `DRAFT -> OPEN (terbit, tanpa approval) -> PARTIAL -> RECEIVED`, plus `CLOSED` (sisa tidak akan datang, dari PARTIAL) & `CANCELLED` (dari OPEN, belum ada penerimaan). Hanya DRAFT yang bisa diedit/dihapus; PO terbit diubah dengan cancel + buat ulang. Baris: `sku`, `uomBeli`, `konversi`, `qty`, `hargaBeli`, `diskonPersen` (per baris), `subtotal`, `qtyReceived` (satuan beli). **Satuan beli** hanya satuan dasar produk (konversi 1) atau satuan di daftar harga vendor tsb untuk SKU itu; konversi selalu diisi backend dari sumbernya (input klien diabaikan), satuan lain ditolak (daftarkan dulu di Vendor Prices). SKU + satuan yang sama maks. 1 baris (UI: pilih SKU lagi = baris satuan lain yang belum dipakai, atau fokus ke qty). Harga disalin dari VendorPrice (boleh diubah per PO); `isPKP` & `taxRate` disalin dari System Settings. Tidak mengubah stok. SKU nonaktif tidak bisa dipesan.
- **Goods Receipt** ([goodsReceiptController](backend/controllers/goodsReceiptController.js)): wajib dari PO OPEN/PARTIAL, gudang = gudang PO, banyak GR per PO. Qty melebihi sisa PO **ditolak** (dicek lagi saat post; dua GR bersamaan bentrok lewat `lock(ref('purchaseOrder', id))`). Post = movement `PURCHASE` (`qtyBase = qty x konversi`, `unitCost`) + HPP + `qtyReceived`/status PO + opsional perbarui VendorPrice dari harga PO (diaudit). Cancel = pembalik (HPP dihitung balik), PO yang CLOSED tetap CLOSED. **Biaya angkut** (`freightCharge`, `freightNote`; tanpa PPN yang bisa dikreditkan): dibagi ke baris menurut nilai (`allocateFreight` di purchaseHelper, sisa pembulatan di baris terakhir; semua nilai 0 -> menurut qty), baris menyimpan `baseUnitCost` (harga PO), `freightCost`, `unitCost` = base + angkut / qtyBase (masuk HPP); hanya diisi / dilihat user `vendorPrice:view` (user lain mengedit draft -> nilai lama dipertahankan). 
- **Tagihan vendor / hutang** ([purchaseInvoiceController](backend/controllers/purchaseInvoiceController.js), `BILL-…`): dari 1 / beberapa GR POSTED vendor yang sama (belum ditagih, tanpa draft retur, PPN PO sama), langsung POSTED, **tidak mengubah stok**. Harga **dikunci** = harga PO (diskon & PPN PO; vendor menagih beda -> diselesaikan di luar sistem / Cost Revaluation); qty = qty GR − yang sudah diretur. **Biaya angkut** GR ditagih oleh `GR.freightVendor` (default vendor PO; boleh ekspedisi lain) sebagai `charges` tanpa PPN tambahan; GR menyimpan `purchaseInvoice` (barang) & `freightInvoice`. Jatuh tempo default = tanggal faktur + `Vendor.termDays`. Sisa = total − `returnedAmount` − `paidAmount` (`invoiceBalance`), status bayar seperti invoice penjualan. Batal hanya tanpa pembayaran aktif (GR bisa ditagih ulang); GR yang sudah ditagih / punya retur tidak bisa dibatalkan. Akses gudang lewat `gudangs` (gudang GR-nya).
- **Pembayaran vendor** ([vendorPaymentController](backend/controllers/vendorPaymentController.js), `VPAY-…` / refund `VRF-…`): 1 pembayaran = 1 tagihan, boleh cicil; PAYMENT <= sisa, REFUND (uang kembali dari vendor) <= kelebihan bayar; batal dengan alasan. Beberapa tagihan sekaligus: pembayaran gabungan (`VPB-…`, lihat Penjualan > Pembayaran gabungan).
- **Retur pembelian** ([purchaseReturnController](backend/controllers/purchaseReturnController.js), `PRT-…`): dari 1 GR POSTED, `DRAFT -> POSTED -> CANCELLED`, alasan wajib, qty <= diterima − diretur (`GR.lines.qtyReturned`). Post = movement `PURCHASE_RETURN` (−qtyBase, `unitCost` baris GR -> HPP rata-rata dihitung ulang) + nilai (harga PO + PPN) mengurangi tagihan GR jika sudah ditagih (`returnedAmount`, `PurchaseReturn.purchaseInvoice`), atau qty yang nanti ditagih. `resolution`: `CREDIT` (potong tagihan) / `REPLACE` (minta ganti: `qtyReceived` PO berkurang, PO terbuka lagi; ditolak jika PO CLOSED/CANCELLED). Cancel = pembalik; ditolak jika GR ditagih ulang setelah retur, atau barang pengganti sudah diterima.
- Dashboard: KPI hutang (sisa, lewat jatuh tempo, jatuh tempo <= 7 hari), pekerjaan tertunda GR belum ditagih & draft retur pembelian. Log audit tagihan & pembayaran vendor hanya terlihat dengan `vendorPrice:view`.
- **HPP masuk per satuan dasar** = harga x (1 − diskon%) [x (1 + PPN%) jika PO non-PKP] / konversi ([helpers/purchaseHelper.js](backend/helpers/purchaseHelper.js)). PKP: PPN tidak masuk HPP.
- PO/GR mengunci & menolak hapus master yang dipakai: Vendor, Gudang, UoM (baris PO), SKU/Produk (`skusWithStockHistory` juga memeriksa baris PO & GR).

### Audit Log

- Koleksi `AuditLog` (append-only; update/delete ditolak oleh hook model): `entity`, `entityId`, `entityLabel` (teks saat itu), `parent` (SKU & harga vendor -> produk), `action` (`create|update|delete|login|login_failed`), `changes: [{ field, label, format, from, to }]` (hanya field yang berubah; relasi `{ id, text }`; password hanya penanda `format: 'secret'` tanpa nilai), `snapshot` (dokumen lengkap saat delete), `batchId` (1 aksi = banyak log, mis. bulk edit / hapus berantai), `user` + `userName`, `ip`, `meta` (alasan login gagal, user agent).
- **Dicatat eksplisit dari controller** lewat [helpers/auditLogger.js](backend/helpers/auditLogger.js) (bukan hook, karena `bulkWrite`/`updateMany` tidak memicu hook):
  ```js
  const before = await audit.snap('vendorPrice', [doc]);   // SEBELUM diubah / dihapus
  await audit.logUpdate(req, 'vendorPrice', before, [doc], { batchId });
  await audit.logCreate(req, 'produkSku', docs);
  await audit.logDelete(req, 'vendorPrice', before, { batchId });
  ```
  Log ditulis **di dalam transaksi yang sama** dengan datanya: gagal menulis log -> seluruh perubahan batal (kecuali log login, yang berdiri sendiri). Simpan ulang tanpa perubahan tidak dicatat.
- Yang dicatat: Produk, ProdukSku (tanpa stok; stok ada di kartu stok), VendorPrice (termasuk vendor yang kehilangan status preferred), Role (izin per resource), User, login (berhasil/gagal), serta Kategori, Vendor, UoM, Variant (nilai: tambah/hapus; urutan saja bukan perubahan), Menu (parent & permission sebagai teks, order), Gudang, Setting, CostRevaluation (baris `SKU: HPP lama -> baru`), PurchaseOrder & GoodsReceipt (GR & PurchaseReturn ber-`parent` PO, histori PO memuat GR & returnya; PurchaseInvoice + VendorPayment (ber-`parent` tagihan); baris sebagai teks `SKU: 10 BOX x 120,000 -5%`), StockAdjustment (status, baris sebagai daftar teks `SKU: +5`; Post/Cancel = update status), Customer, Quotation, SalesOrder (baris `SKU: 2 x 75,000 -10%`, alamat kirim sebagai teks format `address`, persetujuan kredit) & DeliveryOrder (ber-`parent` SO; histori SO memuat DO-nya), SalesInvoice (baris `SKU: 2 x 75,000 -10%`; + shippingCharge, dueDate, returnedAmount, paidAmount, paymentStatus), SalesReturn & SalesPayment (ber-`parent` invoice; histori invoice memuat retur & pembayarannya), dan PriceList (harga `SKU: 75,000`). Definisi field bisa memakai `labels` (kode -> teks) dan format `date` / `stockLines` / `poLines` / `grLines`. **Semua controller yang mengubah data sudah memakai audit.** Entity baru: tambah definisi field di `ENTITIES` (auditLogger), `ENTITY_RESOURCE` ([auditLogController](backend/controllers/auditLogController.js)), dan `ENTITY_META` ([utils/auditFormat.js](frontend/src/utils/auditFormat.js)), lalu panggil helper di controller-nya. **Endpoint baru yang mengubah data entity tsb wajib memanggil audit.**
- `gudangs` (dokumen per gudang) untuk filter akses gudang. Nilai setting gambar (logo) dicatat sebagai `[image N KB · sidik jari]`, bukan isinya.
- Log hanya ada sejak fitur aktif (tidak ada histori sebelumnya); disimpan selamanya.

Pakai token semantik dari [src/index.css](frontend/src/index.css): `bg-page`, `bg-surface`, `bg-subtle`, `text-fg`, `text-muted`, `border-line`, `border-line-soft`, `bg-primary`/`hover:bg-primary-hover`/`text-primary-fg`, `bg-primary-soft`, `bg-nav*`, `bg-side*`, `bg-head`, `bg-highlight`, `text-danger`/`bg-danger-soft`, `bg-warning-soft`, `bg-success-soft`. Teks di atas `bg-primary` selalu `text-primary-fg` (bukan `text-white`, karena tema gelap memakai primary terang).
  - Tema = atribut `data-theme` di `<html>`; tiap tema hanya mengisi ulang variabel `--t-*`. Default `slate-indigo`.
  - Tema tersedia (10): `slate-indigo` (default), `navy-amber`, `emerald-stone`, `light-teal`, `zinc-sky` (gelap), `ocean-coral`, `violet-sunset` (navbar berwarna), `tropical-teal`, `berry-sky`, `aurora` (gelap berwarna).
  - Menambah tema: blok `[data-theme="..."]` di `index.css` (semua variabel `--t-*` + `color-scheme`) + entri di [src/theme/themes.js](frontend/src/theme/themes.js) (`dark: true` untuk tema gelap). Backend hanya memeriksa format id (`THEME_ID` di `authController`); id yang tidak dikenal frontend kembali ke default. Test `frontend/test/utils.test.js` memastikan setiap tema di `themes.js` punya blok CSS lengkap.
  - Pilihan disimpan per user (`User.theme`, `PUT /api/auth/theme`) dan disalin ke `localStorage` key `theme`; script di `index.html` menerapkannya sebelum React render agar tidak berkedip. State: `ThemeProvider` / `useTheme()`.
